문제

에이전트는 "어디를 볼지" 몰라서 다 읽는다

"이 함수 바꾸면 뭐가 깨져?"에 답하려면 호출자, 호출자의 호출자, 테스트까지 따라가야 한다. grep은 현재 소스의 정확한 문자열을 빠르게 찾지만, 호출 관계와 작성 의도까지 이어 주지는 않는다. 둘을 구분하지 않으면 에이전트는 파일을 계속 열고, 컨텍스트 창이 먼저 죽는다.

비용

code-review-graph 자체 측정: flask 전체 코퍼스 143,594 토큰 → 그래프 응답 2,196 토큰.

출처: CRG README 벤치마크 표

정확도

여러 홉을 못 따라가면 영향 범위를 놓친다. 테스트가 안 도는 코드를 "커버됨"으로 착각한다.

반복

세션이 바뀌면 방금 알아낸 구조를 처음부터 다시 알아낸다. 그래프는 디스크에 남는다.

중요: 셋 다 LLM을 내장하지 않는다. 그래프는 구조만 답하고, 자연어 해석은 붙어 있는 에이전트가 한다.

고유점 1 / 3

코드에 "왜"를 적어 넣고, 그걸 검색한다

다른 두 도구는 코드에서 구조만 뽑는다. CCG는 주석에 쓴 업무 규칙까지 그래프에 넣고 검색 대상으로 만든다.

// AuthenticateUser validates credentials and creates a session.
//
// @intent      verify user identity before granting system access
// @domainRule  lock account after 5 consecutive failed attempts
// @sideEffect  writes login attempt to audit_log table
// @mutates     user.FailedAttempts, user.LockedUntil
// @see         ccg://auth-svc/internal/audit/token_audit.go#RecordTokenAudit
func AuthenticateUser(username, password string) (string, error) {

검색이 달라진다

ccg search "payment" 는 이름에 payment가 없어도 @intent·@domainRule에 걸린 함수를 찾는다.

품질 게이트

ccg lint 가 어노테이션을 검사한다: unannotated, incomplete, dead-ref, contradiction, drifted.

대가

사람 또는 AI가 어노테이션을 써 넣어야 값이 생긴다. 안 쓰면 그냥 평범한 코드 그래프다.

고유점 2 / 3

서비스가 여러 개인 조직을 전제로 만들었다

마이크로서비스는 레포가 쪼개져 있다. CCG는 레포마다 namespace를 주고, 그 사이를 잇는 참조를 별도로 관리한다.

namespace 격리

  • ccg build ./backend --namespace backend
  • 한 DB에 여러 서비스 그래프가 섞이지 않는다
  • search·query_graph·list_graph_stats에 namespaces: [] 를 주면 여러 namespace를 한 번에 훑고 결과에 출처 라벨이 붙는다

ccg:// cross-ref

  • 주석에 @see ccg://auth-svc/path/file.go#Symbol
  • 동기화 때 실제 심볼로 해석해 저장
  • get_impact_radius·trace_flow가 cross_namespace: true로 서비스 경계를 넘어 따라간다
  • list_cross_refs로 방향(inbound/outbound)과 해석 상태를 확인

codebase-memory-mcp도 여러 레포를 CROSS_* 엣지로 잇지만, HTTP 경로 매칭 기반이라 오탐 이슈가 열려 있다(#1459). CCG는 사람이 명시한 @see 참조를 해석하는 방식이라 성격이 다르다.

고유점 3 / 3

노트북이 아니라 서버에서도 돈다

Webhook 동기화

GitHub X-Hub-Signature-256 / Gitea X-Gitea-Signature 서명 검증. push 받으면 clone → build → DB 저장까지 자동. 레포별 브랜치 필터(--allow-repo "org/api:main,develop").

브라우저 Wiki

ccg-server --wiki-dir 로 React UI 제공. 트리 탐색, 근거가 붙는 search_docs, 여러 파일을 한 덩어리 Markdown으로 복사하는 Context Tray, Obsidian 스타일 그래프 뷰.

안전한 종료

SIGINT/SIGTERM이 오면 진행 중인 clone·build에 취소 신호를 전파한다. 재시도는 최대 3회, 대기 시간 1s→30s.

세 도구 모두 로컬에서 돌지만, 중앙 서버 하나가 여러 레포 그래프를 최신으로 유지하는 형태를 기본 시나리오로 잡은 건 CCG뿐이다.

code-review-graph는 crg-daemon으로 여러 레포를 감시하고 GitHub Action으로 PR 리뷰를 붙이지만, 웹훅 수신 서버는 아니다. codebase-memory-mcp는 계정 단위 coordination daemon으로 여러 세션을 조율하며, 팀 공유는 graph.db.zst 파일을 커밋하는 방식이다.

그래프에 담는 것

같은 AST에서 서로 다른 걸 뽑는다

CCG

노드 file, package, class, function, type

엣지 calls, contains, imports_from, implements, inherits

추가 어노테이션 태그 10종, namespace 라벨, ccg:// 해석 참조

자기 저장소 색인 결과: 158 파일 · 1,842 노드 · 11,623 엣지

CRG

노드 function, class, import, test

엣지 calls, inheritance, tested-by

추가 엣지 신뢰도 3단계(EXTRACTED / INFERRED / AMBIGUOUS), community 소속, 실행 흐름

fastapi 색인: 1,122 파일 · 6,285 노드 · 27,117 엣지

CBM

노드 Project, Package, Folder, File, Module, Class, Function, Method, Interface, Enum, Type, Route, Resource

엣지 CALLS, USAGE, IMPORTS, DATA_FLOWS, HTTP_CALLS, EMITS/LISTENS_ON, SIMILAR_TO 등

Django 색인: 49K 노드 · 196K 엣지, 약 6초

읽는 법: CBM은 엣지 종류가 가장 많다 — 데이터 흐름, HTTP 호출, 이벤트 채널까지 잡는다. CRG는 엣지에 "얼마나 확실한가"를 붙인다. CCG는 엣지 종류는 적지만 노드에 사람이 쓴 의미가 붙는다.

숫자 읽기

토큰 절감과 검색 품질은 따로 읽어야 한다

CRG의 주장과 단서

질문당 토큰 중앙값 65배 감소 (범위 36~376배).

다만 README가 직접 말한다 — 기준선인 "코퍼스 전체 읽기"는 실제 에이전트가 치르지 않는 상한값이다. 제대로 된 에이전트는 grep 후 몇 파일만 읽는다.

영향 분석 F1 0.693 · 정밀도 0.546. 재현율 1.0은 순환 측정이라 상한선일 뿐.

CBM의 주장과 단서

구조 질의 5개 기준 3,400 토큰 대 412,000 토큰 — 99.2% 감소.

arXiv 프리프린트(2603.27277)는 더 보수적인 숫자를 낸다: 31개 레포에서 토큰 10배 감소, 도구 호출 2.1배 감소, 답변 품질 83%.

같은 프로젝트가 낸 두 숫자가 10배 차이 난다. 측정 조건이 다르기 때문이다.

CCG 검색 회귀선은 생겼고, 토큰 절감 수치는 아직 없다

4개 corpus의 golden 질의를 프로덕션 검색 경로로 replay한다. 주 corpus는 Recall@10 0.747 (127/170), MRR 0.649; 지원한다고 결정한 질문만 보면 Recall@10 0.840, MRR 0.703이다.

한계: 자체 corpus와 판정으로 만든 회귀 하네스다. 외부 독립 평가나 토큰 비용 비교를 대신하지 않는다.

솔직한 정리

CCG의 위치

지금 진짜 앞서는 것

  • 어노테이션으로 업무 의미를 그래프에 넣는 유일한 도구 — 게다가 lint로 품질까지 잡음
  • MSA를 1급 개념으로 다룸: namespace 격리 + 서비스 경계를 넘는 영향 분석
  • 웹훅 수신 → 자동 빌드까지 갖춘 self-host 서버
  • PostgreSQL 지원 — 셋 중 유일
  • 검색 회귀 하네스가 4개 corpus에서 순위·재현율 하락을 막는다

따라가야 하는 것

  • 언어 12개 대 158개 — 격차가 크다
  • 벡터 의미 검색 없음 — 첫 검색 한 방의 명중률에서 불리하다 (다음 장)
  • 외부 독립 벤치마크 없음 — 자체 golden 평가는 제품 간 우열의 증거가 아니다
  • 사용자 규모 17 대 29k 대 38k. 이슈로 버그가 올라오는 양 자체가 다르다

쓰는 방식: 단순 위치는 rg로, 의도·관계·영향은 CCG로 시작한다. “없다”거나 “전부 찾았다”고 결론 내릴 때는 둘을 모두 확인한다.

운영 원칙

grep과 그래프는 경쟁 관계가 아니다

현재 소스의 정확한 증거는 직접 검색이 강하고, 이름에 드러나지 않는 의도와 여러 홉의 관계는 그래프가 강하다. 같은 질문을 서로 다른 각도에서 검증한다.

rg + Read식별자·경로·리터럴·에러 문구
+
ccg search어노테이션·작성 의도 후보
›
Graph walk호출·영향·흐름 확인

결론 내리기 전 체크

  • 정확한 단서가 있으면 rg, 심볼을 모르면 ccg search부터 시작
  • 그래프의 freshness와 truncated·pool_truncated 확인
  • 두 결과를 파일·심볼 기준으로 합치고, 현재 소스에서 최종 확인

진짜 차이

코드에서 뽑을 수 없는 걸 담는다

파싱도 임베딩도 이미 소스에 적힌 것만 다룬다. 더 잘 뽑을 수는 있어도, 없는 걸 만들어 내지는 못한다.

AST가 아는 것 · 모르는 것

  • 안다 — 무엇을 부르고, 무엇을 담고, 무엇을 상속하는지
  • 모른다 — 왜 그렇게 짰는지, 부르기 전에 뭐가 참이어야 하는지, 저 숫자가 왜 하필 그 값인지
  • 임베딩도 같은 벽에 부딪힌다. 표현을 바꿔 줄 뿐 정보를 늘리지 않는다

어노테이션이 넣는 것

  • @domainRule 업무 규칙, 운영 정책, 오탐·미탐 기준
  • @requires · @ensures 부르기 전 지켜야 할 것, 부른 뒤 보장되는 것
  • @sideEffect · @mutates 밖으로 새는 변화
  • @intent 왜 이게 있는지
  • 이게 검색 색인에도 그대로 들어간다 — 코드에 retry라는 글자가 없어도 "재시도"로 찾힌다

if amount > 50000 을 아무리 파싱해도 "5만 원 넘으면 수동 승인이 회사 정책"은 안 나온다. 저쪽은 코드에서 뽑을 수 있는 것의 상한선을 향해 간다. CCG는 그 상한선 밖을 넣는다. "의미 검색이 없는 것 아니냐"의 답도 여기 있다 — 벡터는 소스에 있는 걸 더 잘 찾아 줄 뿐이다.

단서: 어노테이션을 안 단 코드는 이 축이 0이다. 주석이라 코드와 어긋날 수 있고, ccg lint는 품질을 볼 뿐 실제 동작과 맞는지는 검증하지 못한다. 쓰는 단계도 하나 더 필요하다 — /ccg-annotate가 AI로 돕지만 공짜는 아니다.

끝

결론

셋 다 "에이전트가 레포를 통째로 읽지 않게" 만든다. 갈라지는 지점은 무엇을 최적화했는가다.

CBM

속도와 커버리지. 아무 레포에나 던져도 몇 초 안에 답한다.

피한다면: Windows가 주 환경이고 안정성이 최우선일 때.

CRG

리뷰 워크플로. 변경 위험을 PR 위에 얹는다.

피한다면: Python 환경 관리가 부담일 때.

CCG

조직의 맥락. 서비스가 여러 개인 팀에서, 코드가 왜 그런지까지 그래프에 남긴다.

피한다면: 12개 언어 밖의 코드가 많을 때. 검증된 성능 수치가 의사결정에 필요할 때.
